## Challenges and Growth Areas

Amelia (Developer): "Let's talk about where we struggled. The double-safeParse anti-pattern in Story 2.2 stands out — records were being validated twice, once in the fetch layer and again in the transform. It took code review to catch it."

Charlie (Senior Dev): "The hand-rolled interface issue in 2.2 — defining `RawProperty` and `RawAgent` as interfaces in addition to Zod schemas — directly violated the story's own guardrails. The spec said 'do NOT hand-roll', and it still happened."

Dana (QA Engineer): "That one cost a full [Patch] round plus rebuilding the schema exports. The Zod-inferred type approach was then applied cleanly from 2.3 onward. Lesson applied successfully."

Alice (Product Owner): "Story 2.1 had the migration split issue — the extension bootstrap needing its own transaction before the schema migration. That was a runtime surprise, not a design flaw, but it required editing generated SQL by hand. Worth documenting as a known drizzle-kit + PostGIS footgun."

Charlie (Senior Dev): "The deepl-node TypeScript type errors in Story 2.5 are the one open scar. Two pre-existing type errors that didn't regress but weren't cleaned up. That's technical debt with a face."

Elena (Junior Dev): "Story 2.3 had a subtle field name mismatch — `RawProperty.publicRemarksEn` mapping to `properties.description_en` in the DB. The test factories needed to be corrected because they didn't match the actual schema shapes. Small, but it caused a confused debugging session."

Amelia (Developer): "The `amenities.gated` vs `amenities.gatedCommunity` mismatch — same pattern. The test factory shape didn't match the Zod transform output. These are the kinds of seams that ATDD is supposed to prevent, but the factories themselves need to be derived from the actual schema, not written by hand."

**Summary of challenges:**
- Double-safeParse anti-pattern in 2.2 (caught in review, fixed; applied lesson in 2.3+)
- Hand-rolled interfaces duplicating Zod schemas (violating the spec's own guardrails)
- Drizzle-kit + PostGIS extension ordering: a footgun that requires manual SQL editing
- Pre-existing deepl-node type errors from 2.5 not resolved before 2.6/2.7
- Test factory shapes drifting from actual Zod transform outputs in 2.3

## Key Insights

**1. Spec guardrails work when LLMs read them — but they still get violated.**
Story 2.2's spec explicitly said "do NOT hand-roll interfaces" and the agent did it anyway. The defense is code review with a checklist that references the guardrails, not hoping the agent reads them.

**2. The ATDD → Dev → Test Review → Code Review pipeline absorbed complexity well.**
Seven stories, zero pipeline failures, 227 tests at the end. The BAD 7-step pipeline is validated for infrastructure-heavy work.

**3. Incremental pipeline design is worth the upfront investment.**
Writing the hash-based differ in 2.3 and the UNCHANGED-skip pattern across 2.3–2.7 paid for itself. Each new pipeline stage (images, translation, tags) could be integrated without rewriting existing stages.

**4. `deferred-work.md` is the right place for code review deferrals.**
Having one canonical file that accumulates all deferred items across stories gives a clean audit trail for the next epic's planning. Epic 3 preparation should start with a pass over this file.

**5. The `server-only` directive is the correct security boundary mechanism.**
Build-time enforcement is better than convention. No accidental client imports across 7 stories, 14+ new files in `src/lib/sync/`.

**6. PostGIS + Drizzle has one known footgun: extension bootstrap ordering.**
`CREATE EXTENSION` must run in its own transaction before the schema DDL. This is now documented in `docs/database/README.md` but future migrations need to be aware. If using `drizzle-kit generate`, always inspect the generated SQL before running it.

**7. Test factory accuracy is a hidden risk in ATDD.**
The scaffolded tests were high-quality, but the factory objects used in those tests must exactly match the Zod schema output shapes. Mismatches (`gatedCommunity` vs `gated`, missing `name` on `RawAgent`) caused confusion in 2.3. Future ATDD should derive factory defaults from the actual schema, not from memory.
